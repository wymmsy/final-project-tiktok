# Проверка конвенций TikTokFeed

Эта skill оборачивает статический чекер `scripts/check_architecture.py` и
объясняет его результат в терминах архитектуры проекта, описанной в
[AGENTS.md](../../../AGENTS.md). Скрипт ничего не чинит и не запускает
build — только читает `*.cs`/`*.json` через regex и печатает список
нарушений.

## Когда применять

- После любых правок в `src/**/Domain`, `src/**/Application`,
  `src/**/Infrastructure` или `src/**/Api` (новая сущность, репозиторий,
  контроллер, use case).
- Перед тем как сообщить пользователю, что задача с изменением кода
  завершена.
- По прямому запросу вроде «проверь конвенции», «прогони линтер»,
  «есть ли архитектурные нарушения».

## Шаги

1. Запусти скрипт из корня репозитория:

   ```bash
   python3 scripts/check_architecture.py
   ```

   Если менялись файлы вне `src/` (например, тесты) или нужно сузить
   область — передай `--path`:

   ```bash
   python3 scripts/check_architecture.py --path src/Content.Domain
   ```

2. Прочитай вывод построчно. Формат: `[SEVERITY] rule-id  file:line — сообщение`.
   В конце — сводка `Нарушений: N (error: X, warning: Y, info: Z)`.

3. Отсортируй находки по важности для ответа пользователю:
   - **error** — реальные нарушения архитектуры (см. таблицу ниже),
     требуют исправления перед коммитом.
   - **warning** — нужно посмотреть глазами, среди них попадаются
     ложные срабатывания (см. "Известные ложные срабатывания").
   - **info** — как правило, не блокирует (например, dev-секреты в
     `appsettings.json`), но стоит упомянуть.

4. Для каждого `error`/`warning` открой указанный файл и строку, чтобы
   подтвердить находку перед тем, как докладывать её пользователю —
   скрипт работает по regex и может ошибаться на нетипичных конструкциях.

5. Если нашлись реальные нарушения — предложи или сразу внеси
   исправление, следуя правилам из [AGENTS.md](../../../AGENTS.md)
   (например, вынести доступ к `DbContext` из контроллера в
   репозиторий, заменить `Console.WriteLine` на `ILogger`).

6. После исправлений прогони скрипт повторно, чтобы убедиться, что
   `error`-находки закрыты, и только после этого отчитывайся о готовности.

## Таблица правил

| rule-id | severity | суть |
|---|---|---|
| `domain-layer-isolation` | error | Domain ссылается на Application/Infrastructure/Api/EF Core/ASP.NET Core |
| `application-layer-isolation` | error | Application ссылается на Infrastructure/Api |
| `no-dbcontext-in-controller` | error | `DbContext` используется напрямую в контроллере/gRPC-сервисе |
| `empty-catch-block` | error | Пустой `catch {}` |
| `no-async-void` | error | `async void` вместо `async Task` |
| `no-console-write` | warning | `Console.WriteLine`/`Write` вместо `ILogger` |
| `sync-over-async` | warning | `.Result`/`.Wait()` — возможное блокирующее ожидание Task |
| `interface-naming` | warning | Интерфейс без префикса `I` |
| `todo-comment` | info | Оставленный `TODO`/`FIXME`/`HACK` |
| `hardcoded-secret` | info | Пароль/секрет в `appsettings*.json` |

## Известные ложные срабатывания

- `sync-over-async` на `outcome.Result` в `src/Shared/Resilience/HttpResiliencePolicies.cs` —
  это `.Result` объекта Polly (`DelegateResult<HttpResponseMessage>`), а не
  `Task.Result`. Не является блокирующим ожиданием, можно игнорировать.
- `hardcoded-secret` в `appsettings.json` трёх `*.Api` проектов — dev-заглушки
  (`Password=postgres`, JWT `Secret`), совпадающие с `docker-compose.yml`.
  Это ожидаемо для локальной разработки; флагом стоит помечать только если
  такое же значение попадёт в конфиг для prod-окружения.

## Область действия и ограничения

- Скрипт сканирует только `*.cs` и `*.json` под `src/` (по умолчанию) —
  `tests/`, `mocks/` и корневые конфиги не проверяются.
- Это regex-эвристики, а не полноценный Roslyn-анализ: он не понимает
  семантику типов, поэтому возможны как ложные срабатывания (см. выше),
  так и пропуски (например, обход правила через алиасы `using X = ...`).
  Итоговое решение — за агентом, скрипт лишь сужает область поиска.
